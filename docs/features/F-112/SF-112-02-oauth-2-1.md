## Objectif

Faire de l'application un **serveur de ressources** OAuth 2.1 pour `/api/mcp` **et** un **serveur
d'autorisation** embarqué (Spring Authorization Server), avec PKCE obligatoire, audience vérifiée,
`iss`, enregistrement dynamique + CIMD, rafraîchissement rotatif, révocation, rotation des clés et
écran de consentement, chaque partie sur sa **chaîne de filtres séparée**, sans rien ouvrir ailleurs.

---

## Comportement attendu

### Cas nominal

1. Un client IA découvre l'autorisation : `GET /api/.well-known/oauth-protected-resource` (RFC 9728)
   donne la ressource `/api/mcp` et son serveur d'autorisation ; `GET
   /api/.well-known/oauth-authorization-server` (RFC 8414) donne les endpoints.
2. Le client lance le flux **code d'autorisation + PKCE** : `/api/oauth2/authorize` ; l'utilisateur,
   connecté dans son navigateur, voit l'**écran de consentement** (nom du client, périmètres en
   français) et accepte ; la réponse porte `code` et `iss` (RFC 9207).
3. `/api/oauth2/token` échange le code (avec `code_verifier`) contre un **jeton d'accès** court (15 min,
   `aud` = ressource `/api/mcp`) et un **jeton de rafraîchissement rotatif**.
4. Le client appelle `/api/mcp` avec `Authorization: Bearer <jeton d'accès>` : le serveur de ressources
   valide la signature (JWK du serveur d'autorisation), l'expiration et l'**audience**.
5. `/api/oauth2/revoke` révoque un jeton ; `/connect/register` enregistre dynamiquement un client
   (CIMD accepté).

### Cas d'erreur (tests d'attaque)

| Situation | Comportement attendu | Code |
|-----------|---------------------|------|
| Jeton d'accès dont `aud` n'est pas `/api/mcp` | Refus | 401 sur `/api/mcp` |
| `/oauth2/authorize` sans `code_challenge` (PKCE) pour un client qui l'exige | Refus | 400/redirect erreur |
| `redirect_uri` non déclarée par le client | Refus | 400 |
| Périmètre demandé plus large que ceux du client | Refus `invalid_scope` | 400/redirect erreur |
| `/api/mcp` sans jeton | Refus + `WWW-Authenticate` vers la métadonnée de ressource | 401 |
| Jeton MCP présenté sur une route hors `/api/mcp` | Refus (aucune route ouverte) | 401/403 |

## Critères d'acceptation

- [ ] `/api/.well-known/oauth-protected-resource` renvoie la ressource et le(s) serveur(s) d'autorisation (RFC 9728).
- [ ] `/api/.well-known/oauth-authorization-server` est servi par le serveur d'autorisation (RFC 8414).
- [ ] Le flux code + PKCE (S256) fonctionne ; PKCE **obligatoire** ; `iss` présent (RFC 9207).
- [ ] Le jeton d'accès porte `aud` = ressource `/api/mcp` ; le serveur de ressources vérifie l'audience.
- [ ] Rafraîchissement **rotatif** ; révocation disponible ; clés de signature exposées en JWK et **rotables**.
- [ ] Enregistrement dynamique de client + CIMD acceptés.
- [ ] Écran de consentement affiché (nom du client, périmètres en français).
- [ ] **Chaînes séparées** `/api/mcp`, `/oauth2/*` (+ `/connect/register`), `/.well-known/*`, sans rien
      ouvrir ailleurs.
- [ ] **Non-régression** : un jeton MCP n'ouvre **aucune** route hors `/api/mcp` ; toutes les routes
      existantes gardent leur authentification (JWT plateforme + Google inchangés).
- [ ] Les 4 tests d'attaque du cadrage passent.

## Contraintes de validation

| Champ | Règle |
|-------|-------|
| Jeton d'accès | JWT signé RS256 (JWK du serveur d'autorisation), TTL 15 min, `aud` = ressource MCP |
| PKCE | obligatoire (S256) pour les clients MCP |
| Rafraîchissement | rotatif (non réutilisable), révocable |
| Périmètres OAuth | `postes:lire postes:agir terminaux:ecrire radar:lire radar:ecrire pages courriel compte:lire admin` (cadrage §4) |
| Ressource MCP | `app.mcp.resource` (défaut construit sur l'origine + `/api/mcp`) |

## Technique

### Endpoints (serveur d'autorisation + métadonnées, tous sous context-path `/api`)

| Méthode | URL | Chaîne | Auth |
|---------|-----|--------|------|
| GET | `/api/.well-known/oauth-protected-resource` | métadonnées | publique |
| GET | `/api/.well-known/oauth-authorization-server` | AS | publique |
| GET/POST | `/api/oauth2/authorize` | AS | session navigateur (login existant) |
| POST | `/api/oauth2/token` `/api/oauth2/revoke` | AS | client |
| GET | `/api/oauth2/jwks` | AS | publique |
| POST | `/api/connect/register` | AS | enregistrement dynamique |
| GET/POST | `/api/oauth2/consent` | AS | session navigateur |
| POST/GET/DELETE | `/api/mcp` | ressource | jeton d'accès OAuth (audience) |

### Tables impactées

Aucune migration en SF-112-02 : registre de clients et autorisations **en mémoire** (les clients MCP
s'enregistrent dynamiquement / par CIMD ; la persistance des clients et des jetons est traitée avec le
journal et les jetons personnels en SF-112-03). Décision documentée dans la PR.

### Composants

- `AuthorizationServerConfig` — `SecurityFilterChain` SAS (`@Order`), `RegisteredClientRepository`,
  `AuthorizationServerSettings`, `JWKSource` rotable, `OAuth2TokenCustomizer` (aud + scopes),
  `JwtDecoder`.
- `McpResourceServerConfig` — remplace la validation JWT interim de SF-112-01 sur `/mcp` par un
  serveur de ressources OAuth (audience validée) + entry point `WWW-Authenticate` RFC 9728.
- `ProtectedResourceMetadataController` + sa chaîne de sécurité publique.
- `McpConsentController` — écran de consentement (page d'infrastructure OAuth).
- `McpScopes` — la liste des périmètres et leur libellé français.

### Préoccupations transversales — composants impactés (auth / Principal)

- `SecurityConfig` (chaîne principale) : **inchangée** ; vérifiée par test de non-régression (routes
  existantes gardent leur auth).
- `McpSecurityConfig` (SF-112-01) : la validation du porteur passe de JWT interim à jeton d'accès OAuth.
- `OAuth2ClientConfig` (login Google entrant) : **inchangé**.
- `CurrentUser` / `AuthenticatedUser` : inchangés ; le principal de la ressource MCP reste résolu via
  le contexte d'appel MCP.
- Tous les endpoints existants : couverts par le test de non-régression (un jeton MCP ne les ouvre pas).

## Notes et décisions

- Registre de clients et service d'autorisation **en mémoire** en 02 : les clients MCP se déclarent par
  enregistrement dynamique / CIMD, et un client de démonstration (`claude-code`) est enregistré pour
  les tests. La persistance (clients, jetons, journal) arrive en SF-112-03.
- La rotation des clés est réelle (source JWK à plusieurs clés, clé courante de signature, anciennes
  conservées pour la validation) ; la rotation périodique est désactivée en test.
- L'écran de consentement est une **page d'infrastructure OAuth** (rendue par le backend), pas un
  composant produit Angular ; l'écran « IA connectées » (produit) est en SF-112-03.
